# 赛程数据生产服务与赛季排名仓 — 设计说明

虚构联赛，4/6 队单循环。两个仓各自独立持久化（真实 SQLite 文件，可关闭重开复算），
赛程服务对积分/资格零推断，排名仓以只读 URI 连接赛程库。

## 2. 赛程服务：整关系校验与 edition 模型

### 固定什么、可变什么
初始化后固定三件事：球队 ID 集合、`match_id` 集合、每个 `match_id` 的 `round`。
新候选只能重新安排未开打的同轮双方、主客与 slot（本题所有发布均在赛季开始前）。
每次合法发布产生一个递增 `edition_id`，并在 `edition` 表内快照当时的 slot 容量与
球队禁用规则；旧 edition 的行在 `edition_match` 中永不更新，修订只插入新行。
因此“赛程校正后仍按旧归属入表”的问题在结构上不可能发生：事实只按显式请求的
edition 解释，旧 edition 永远返回旧关系，新 edition 返回新关系，二者可并存查询。

### 校验是整关系核对，不是逐场放行
`check_candidate` 对整份候选一次性给出全部可定位 `Issue(code, location, message)`，
`publish` 只是“校验 + 单事务插入”，不存在先逐场发布再补齐整轮的路径。校验层次：

1. 行级：字段、未知球队/match_id、自己对自己、round 与固定骨架不一致、
   slot 不在轮次声明内、球队禁用 slot。
2. 骨架完整性：固定 match_id 一条不能少、候选内不能重复。
3. 单循环：球队对集合恰好等于全部 `C(N,2)` 个无序对（漏配/重复配对）。
4. 轮次：每轮每队恰好一次（整轮缺队/一队两次）、每轮 N/2 场。
5. slot：按 `(round, slot)` 聚合不超容量；同轮同队同 slot 重复独立报错。
6. 主客：全季 home/away 次数差 ≤ 1；按 round 滑窗检查无连续三轮同角色。

可用性问题（禁用、slot 不允许）不把行标记为结构无效，避免一条坏行级联出
“整轮缺队”等噪音；结构约束仍在同一次检查中独立报告。

### 与独立 oracle 的双向对照
`oracle.enumerate_legal_schedules` 在 4 队小域用回溯枚举所有完美匹配 ×
主客方向 × slot 赋值，再独立复核全局约束。测试断言：枚举内每个候选服务都放行、
枚举外的破坏样本服务都拒绝；禁用使枚举空间收窄为空时，服务同样无合法候选。

## 3. 排名引擎：递归小表为什么必须重算

`league/ranking.py` 是不依赖存储的纯函数，输入“fixture 投影 + 结果映射 +
判罚 + 轮次范围”，输出最终名次与完整 `tie_tree` 解释。

### 数据流
1. 只收集轮次范围内 `state == 'played'` 的比赛；`cancelled/pending` 进
   `ignored_matches` 并带原始 state，绝不补 0:0。
2. 比分按传入 fixture 的 home/away 归属到球队（胜 3/平 1/负 0），累计全表
   场次、进球、失球、净胜分。
3. 总积分 = 比赛积分 − penalty_points（可为负）；判罚不进入任何小表。
4. 按总积分降序形成同分集合，逐组递归。

### 递归规则（对应题面，防“全季净胜分冒充相互小分”）
- 对同分集合 S，只挑双方都在 S 内的 played 比赛，计算小表积分/净胜分/进球数，
  三指标作为**一个整体键**分组，按键降序排列。
- 若拆出多个真子组：每个仍多于一队的子组，用**子组自身**相互比赛重新计算三指标
  后递归（`tests/test_standings.py::test_split_two_plus_two_and_recompute`
  构造 4 队同分拆成 2+2，断言子组小表积分是 1 而不是沿用大集合的 7）。
- 若三指标完全不能拆分：退到请求轮次范围内的全表净胜分、进球数，再按球队 ID
  ASCII 顺序，叶子化终止。
- 每个节点记录 `teams / match_ids / metrics / criterion / split_used / children`，
  实际使用的比赛 ID 与每层指标都可审计，不只暴露最后一个排序键。

case.json 的 before 投影即是一个活反例：A/B/C 同 6 分，全季净胜分 B(+3)>C(+2)，
但相互小表里 C 的进球 3 > B 的 2，正确顺序 C>B>A；引擎输出与显式手算一致。

## 4. 事实仓：原子批、身份语义与切面快照

### 比分事实
- `request_log` 保存每个 request_id 的规范化内容哈希：同号同文直接复读原回执，
  同号异文（含类型变化）拒绝。
- 每批先做完整校验再开事务：未知 match_id、批内 result_id 重复、非法 state、
  played 分数越界（非 0..100 整数/布尔值）、非 played 携带比分、同 match 已存在
  不同 active result_id —— 任一命中整批拒绝，库内无流水、无事实行。
- `result` 表全量保留历史行，部分唯一索引
  `ux_active_result_id` / `ux_active_match`（SQLite 过滤索引）在数据库层兜底
  “一个 result_id 一个 active 身份”“一个 match 一个 active 身份”。同 result_id
  的新批次把旧行置 `active=0` 再插新行，实现按接收 seq 的完整替换；
  新 result_id 指向已有 match 会在业务校验中被拒，不会被当成另一场比赛。

### 判罚事实
独立流水 `penalty_event`（apply/revoke）+ 物化 `penalty_state`。
单队累计上限 9，超界整批回滚；revoke 清零并留痕。判罚批次同样走 request_id
幂等与原子校验，且永不改写比分或赛程。

### 排名请求是切面快照
`standings(request_id, edition_id, (from, through), 名额)` 在当下事实切面上计算，
结果整体 JSON 落 `standings_snapshot`，记录 `edition_id / seq_floor / 轮次范围 /
名额`。之后任何事实追加或替换都不触碰旧快照；重开库后 `get_snapshot` 原样返回，
满足“之后修改不改写旧结果”。当前已知 played 不全时照常出排名，`ignored_matches`
与各行 played 数如实反映进度，不谎称赛季终局。

## 5. 断链对照（demo.py 第 5、6 节）

固定比分事实与 request 身份，发布两个都合法的 edition（before / after，
翻转 ab、ac、bc 三场，覆盖全部三轮各一场）。

- 显式请求 after：引擎读取 after fixture，槽位比分按新主客归属，
  升级队为 A（快照 `rank-after`）。
- 断链消费者：请求身份仍是 `rank-after` + edition 2，但内部冻结 before 投影
  调用同一纯函数引擎，得到 before 的名次，升级队变成 C，A 的进球 13 被错算成 11。
  错误以具体积分/进球/资格差异呈现，没有改动任何最终名次来伪造断链。
- 控制对照：显式请求旧 edition 的 `rank-before` 完全合法，其数值恰好等于断链
  投影——区别只在请求身份与所用投影是否一致。两个请求的 request_id 与 edition
  身份在对照中保持各自固定，可逐条审计。

## 6. 两种可行组织的成本、解释力与旧切面一致性取舍

### 方案 A：整关系核对 + 全量重算（本实现采用）
- **做法**：候选赛程整份重扫所有约束；排名请求在当前 active 事实上全量重算，
  结果以快照持久化。
- **成本**：每次校验/排名 O(N² + 结果数)，4/6 队域是微秒级；存储保留全部历史行，
  写放大随批次数线性增长。无需自造平衡树或增量索引，代码直白、可整体审计。
- **解释力**：天然能给出每层球队集合、实际 match_id 与全部指标，因为解释就是
  重算过程本身；oracle 可以用完全独立的枚举/累加实现交叉验证。
- **旧切面一致性**：最强。快照是不可变 JSON，历史请求与当时事实、edition 永久
  绑定，后续写入物理上不可能改写旧答案。
- **代价**：不随规模扩展到大型联赛；高并发写入依赖 SQLite 单写者事务，
  批量接收需排队。

### 方案 B：按轮/同分组维护增量约束索引与物化小表
- **做法**：为 slot 容量、球队轮次出场、主客计数、同组小表指标维护增量索引，
  候选只重算受影响的轮/组；排名维护各级分组的物化指标，事实变更时定向更新。
- **成本**：单次校验/更新可降到 O(变化规模)，读路径快；但索引种类多、一致性
  维护复杂，替换批次（result_id 完整替换）需要可逆的差额更新，bug 面显著更大。
- **解释力**：能解释当前状态，但“当时为什么这样排”需要额外的事件溯源或
  周期快照，否则增量覆盖后旧小表数值丢失——恰是题面“用全季净胜分冒充相互小分、
  子组不重算”这类错误最容易潜伏的地方。
- **旧切面一致性**：必须配合快照/事件日志才能等价于方案 A；只维护当前物化视图
  会让历史排名请求被新事实悄悄改写。
- **适用**：球队数与并发量大、在线读延迟敏感的场景；本题小域明确不需要，
  选 A 以换取可证明的正确性与完整解释。

## 7. 边界与不做的事
不做自动排程搜索/最优赛程、网页、实时采集、投注或真实赛事接口；不实现开赛之后
的改赛（所有 edition 发布均在赛季开始前）。赛程服务任何接口都不返回积分或资格。

## 8. 旧场记簿逐球卡：解释引擎、制胜球与奖务排庭

### 8.1 事实模型与两类数据产品
旧场记簿每场已 played 比赛持有一卷具名逐球卡（`league/playbyplay.py`）：
卡按具名序号 1..N（N<=30）排列，每卡正好一球，给出一或两个可能记入方
（home/away）及该记入方下实际记载的球员。建产品时按当版 fixture 的主客球队与
球员名册过滤卡面：球队不符的选择被排除并写入 `excluded` 留痕，绝不进入解释。
终场主客得分只从冻结事实取（或显式入参），不由卡面推断；取消场单独标 status，
解释阶段直接不出奖凭单。

两个可独立重开的数据产品：

* **记分员侧** `PlayByPlayProduct`：过滤后的卡卷、名册、检查点与终分，整体 JSON
  可序列化，关闭库后凭载荷原样重建。
* **奖务桌侧** `InterpretationReport`：整卷解释（可行性、首个无合法前缀卡、
  制胜卡集合、每卡合法记入方、两条完整见证、分层状态审计）。奖务判定只消费它，
  不回看活账；同一份产品配合不同奖务登记可反复重算。

### 8.2 为什么用分层状态图而不是枚举排列
一条合法解释必须从 0:0 逐球走到实际终分并经过全部累计检查点，且**不准把不同
解释上的前后两球拼在一起**。引擎把状态空间定义为“第 k 卡后的累计比分
(home, away)”，前向建 `parents[k][state]` 边图（保留全部转移，不按检查点剪枝），
再分别做两次独立传播：

1. 前向 `prefix_ok`：从 0:0 出发、逐卡满足检查点的状态，定位**首个无合法前缀的
   卡**；空层只代表终分上界剪枝，不算前缀死亡。
2. 后向 `can_finish`：从终分沿前驱、且只穿过 `prefix_ok` 状态传播，判定终分
   可达性。各卡前缀都活着而终分不可达时标 `"final"`（矛盾到终场才暴露）。

状态数只受终分约束（30 卡时单层至多百余状态），与 2^N 排列数无关，因此整场
不保存任何一种排列。独立 `oracle_cards.py` 在 <=12 卡小域上做直白笛卡尔积
枚举，测试断言两条实现的合法球序、制胜卡、收件者、可共现结论逐项一致。

### 8.3 制胜球与不拼接见证
制胜球定义为“最终胜队最后一次与对手打平之后，第一次建立并一直保持领先的那粒
球”。引擎在合法子图上按状态传播“最后一次平局位置”的**集合**（平局状态重置为
当前层，非平局沿前驱传播），终场状态上的该集合 +1 即全部可能制胜卡，全程不
枚举球序。需要听审见证时，`_build_trace` 为每个 `(状态, 最后平局位置)` 留一个
前驱指针，按目标制胜卡线性回溯出一条完整路径；两条见证按不同制胜卡取，天然
足以说明收件者分歧。平局不产生制胜球。

`can_cooccur` 用同一套分层可达 DP 回答“若干钉选的卡/记入方能否出现在同一条
真实记录里”：所有钉选必须在同一条 0:0→终分路径上同时成立，跨解释拼接的钉选
组合在状态图上本就不连通，返回 False。

### 8.4 发证三态与“无人能领”
`league/awards.py` 把制胜卡映射到收件者：球员奖即卡面球员；培训站奖按奖方
**自己的注册簿** player→station 归并，未登记球员该解释为 `None`（无人能领）。

* 所有合法解释收敛到同一具体收件者 → `issue`，立即发一份奖证（即使制胜卡
  仍有歧义，例如 P/Q 同属 K 时直接发 K）；
* 多个具体收件者，或有人/无人并存 → `pending`，开真实收件争议听审案，附两条
  完整见证、可能收件者、具名原件卷号与实际保管人；
* 平局/不可解释/取消场，或全部解释无人能领 → `none`，不颁。无人能领没有代理人。

### 8.5 听审排庭的约束与目标次序
`league/tribunal.py` 是纯约束求解，输入只有冻结案件、主席可用日与回避清单。
硬约束：每庭占一整天；主席与保管人是不同的人；同一人一天只在一庭；同场两案
可合庭（须有一位对两案都不回避的主席，共传保管人一次）也可分庭；任一可能
收件者命中主席事先登记的回避清单即不得主持；每批最多三场/六案/四主席/五天。

求解目标按字典序：**传卷次数最少 → 同样少传时最早收完**。每场先生成合庭/分庭
两类结构选项（至多 2^3=8 种），再对固定结构回溯指派 (天, 主席)，日子从 1 起
试以偏向尽早；`summon_cap` 支持馆方查询“给定传卷上限最快哪天审完”。立即能签
的奖在 `awards` 阶段就发掉，排庭模块从不为待核案“预约”出获奖人。

### 8.6 持久化：版本化冻结与关账重算
`league/card_repo.py` 用独立 SQLite，只读连接赛程库取当版主客。卡卷按
`(match, edition)` 版本化：比分或卡面涂改订正后另发新版本，老版整卷保留；
request_id 同号同文复读、异文拒绝，结构非法整卷回滚无流水。冻结解释与奖证
各自整体 JSON 落快照，之后关账或更换奖务登记都不改写旧快照——演示第 5、10 节
验证关闭成绩/事实库后，仅凭同一份冻结产品即可按不同培训站注册簿重新判定与
排庭，关闭重开后版本、流水、快照、奖证全部可复算。
